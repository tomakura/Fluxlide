# 技術検証: 上映ウィンドウ

> 実施日: 2026-10-20。macOSの内蔵ディスプレイと、Sidecar（iPadをサブディスプレイとして使う機能）で確認した。ケーブルでつないだ外部ディスプレイ、Windows、Linuxでは未確認。

## 1. 目的

[技術選定](tech-stack.md)の「最初に検証する技術課題」2番（メイン画面を操作しながら外部モニターへ出力を続けられるか）について、上映ウィンドウの実装方式を決める。候補は次の2つ。

- Tauriのウィンドウにwgpuで直接描画する
- winitで作った別プロセスのウィンドウに描画する

## 2. 試作した方式

Tauriの `unstable` 機能で使える `tauri::window::WindowBuilder` で、webviewを持たないネイティブウィンドウを作り、そのウィンドウにwgpuのサーフェスを作って描画する。

| 項目 | 実装 |
| --- | --- |
| ウィンドウ | 枠なし・タスクバー非表示で、選んだ画面の位置に作り、その画面で全画面表示する。カーソルは隠す |
| サーフェス | macOSのAppKitの制約に合わせ、メインスレッドで作成する |
| 描画 | 専用スレッドでループする。`PresentMode::Fifo` で垂直同期に合わせて表示する |
| サイズ変更 | ウィンドウの `Resized`・`ScaleFactorChanged` イベントを受けて、次のフレームでサーフェスを設定し直す |
| 終了 | 管理画面の「上映を終了」、または上映ウィンドウでEsc。管理画面を閉じると上映も止まる |
| 計測 | フレームレート、直近1秒の最大フレーム間隔、遅れたフレーム（平均間隔の1.5倍超）、描画を省いた回数を管理画面に表示する |

テストパターンは、紺の背景、4秒で画面を横切るコーラルのバー、10等分の補助線、画面の四辺に接する白枠からなる。バーの動きでカクつきを、白枠で全画面が画面の端まで覆っているかを確かめる。

関連するコード:

- [`crates/fluxlide-engine/src/presenter.rs`](../crates/fluxlide-engine/src/presenter.rs): ウィンドウへの描画
- [`crates/fluxlide-engine/src/test_pattern.wgsl`](../crates/fluxlide-engine/src/test_pattern.wgsl): テストパターン
- [`src-tauri/src/presentation.rs`](../src-tauri/src/presentation.rs): ウィンドウ作成、描画スレッド、Escの扱い

## 3. 確認環境

| 項目 | 内容 |
| --- | --- |
| OS | macOS 27.0.1 |
| 機種 | Apple M4 Pro（Metal 4） |
| 画面 | 内蔵ディスプレイ 3456×2234（Retina、拡大率2）<br>Sidecar 1600×1112・60Hz（AirPlay接続、拡大率1） |
| 主なバージョン | Tauri 2.12.4、wgpu 30.0.1、tauri-plugin-global-shortcut 2.4.1 |

## 4. 結果

| 確認項目 | 結果 |
| --- | --- |
| webviewなしのTauriウィンドウにwgpuで描画できるか | できた |
| 全画面で画面の四辺まで覆えるか | 白枠が四辺すべてに表示された |
| 描画が滑らかか | 目視でバーのカクつきは見られなかった。計測値は記録していない |
| 選んだ画面に表示されるか | Sidecarを選ぶとSidecarに表示された（下記の修正後） |
| 上映中に管理画面を操作できるか | 未確認。管理画面と上映画面を別々の画面に置いた状態での操作は確かめていない |
| 上映ウィンドウでEscを押して終了できるか | できた（下記の対応後） |

### 選んだ画面に表示されない問題

最初の実装では、Tauriの `set_fullscreen_on_monitor` で全画面にしていた。Sidecarを選んで上映を始めると、内蔵ディスプレイに表示された。

`set_fullscreen_on_monitor` は、渡した物理座標を含む画面を探して全画面にする。macOSの物理座標は画面ごとの拡大率で換算されるため、拡大率の違う画面が混ざると座標の範囲が重なる。今回は、Sidecarの位置が内蔵ディスプレイの範囲に入り、先に見つかった内蔵ディスプレイが選ばれていた。

現在は、ウィンドウを選んだ画面の位置に作ってから、そのウィンドウがある画面で全画面にしている。macOSでは位置を論理座標（物理座標をその画面の拡大率で割った値）で指定する。この変更後、Sidecarに表示されることを確認した。WindowsとLinuxでは物理座標で移動させているが、未確認である。

### Escキーの扱い

webviewを持たないウィンドウにはTauriのキーボードイベントが届かない。そのため、上映ウィンドウが前面にある間だけ、Escをグローバルショートカットとして登録している。

最初の実装では、上映ウィンドウが前面に来たというイベントを受けてから登録していた。macOSでは全画面のスペースへ移る際にこのイベントが届かず、開始直後にEscが効かなかった。仮想デスクトップを切り替えて戻ると効いた。

現在は、上映を始めた時点でEscを登録し、上映ウィンドウが背面に回ったときと管理画面が前面に来たときに登録を外している。この変更後、開始直後でもEscで終了できることを確認した。

上映ウィンドウでのEscは、確認なしですぐに上映を終える。[画面草案](ui-draft.md)の「上映終了は確認ダイアログ」は管理画面の操作を対象としている。

## 5. 判断

macOSでは、Tauriのウィンドウに直接描画する方式で上映ウィンドウを実装できる見込みが立った。winitの別プロセスは現時点では使わない。ただし、次の確認が終わるまでは方式を確定しない。

## 6. 未確認の項目

- ケーブル（HDMIなど）でつないだ外部ディスプレイへの出力。今回はSidecarでのみ確認した
- 管理画面と上映画面を別々の画面に置いたときの操作感と、Escの登録の挙動
- 上映中のディスプレイの抜き差し、解像度やリフレッシュレートの変更
- WindowsとLinuxでの動作。特に次の点
  - Windows: WebView2でウィンドウ作成がデッドロックしないか（非同期コマンドで作成している）
  - Linux: Waylandではグローバルショートカットが使えないため、Escの代わりの方法が要る。X11（仮想ディスプレイ）では、GTKのウィンドウへのwgpuの描画面の作成、全画面表示、Escでの終了を確かめた（[Linuxでの確認](check-linux.md)）
- フレームレートなどの計測値の記録
- Tauriの `unstable` 機能に依存する点。将来のバージョンでAPIが変わる可能性がある
- GPUの選び方。描画エンジンはウィンドウを作る前にGPUを選ぶため、複数のGPUがある環境では、上映ウィンドウに表示できないGPUを選ぶおそれがある。現在はその場合にエラーを返すだけで、上映ウィンドウに合わせてGPUを選び直す処理はない
- LinuxのWaylandでOpenGL ES（GLES）を使う場合、wgpuのインスタンスに表示ハンドルを渡す必要がある。現在は渡していない
