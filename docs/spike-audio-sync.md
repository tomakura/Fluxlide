# 技術検証: 動画の音声と映像の同期

> 実施日: 2026-10-20。macOSで、描画エンジン単体での計測と、上映ウィンドウで目と耳による確認を行った。Windows、Linuxは未確認。

## 1. 目的

[技術選定](tech-stack.md)の「最初に検証する技術課題」4番（音声同期とBGMフェードを破綻なく扱えるか）の入口として、次の2点を決める。

- 動画の音を取り出して鳴らす方式
- 音を映像と同じ時刻に合わせ、クロスフェードでは音量もつなぐ仕組み

BGMとBluetooth機器の遅延補正は対象外とする。

[写真と動画の連続再生](spike-media-playback.md)の試作では、動画の音を再生していなかった。

## 2. 方式

### 音声出力の候補

| 候補 | ライセンス | 3OSへの対応 | 映像の時刻に合わせやすいか |
| --- | --- | --- | --- |
| **cpal** | Apache-2.0 | macOSはCore Audio、WindowsはWASAPI、LinuxはALSA。LinuxではビルドにALSAの開発用パッケージが要る | 出力機器が求める分だけ自分で波形を渡す。機器が報告する「渡した音が聞こえる時刻」を使える |
| rodio | MIT または Apache-2.0 | cpalを使っている | 再生とミキシングを引き受けてくれる。ただし再生位置は自身の時計で進むため、外の時計に合わせる仕組みを足す必要がある |
| OS標準のAPIを直接使う | OSのライセンス | OSごとに別の実装が要る | 細かく制御できる |

### 動画から音を取り出す方法の候補

| 候補 | 内容 |
| --- | --- |
| **映像とは別のffmpegプロセスで取り出す** | 1本の動画につき、映像用と音声用の2つのプロセスを動かす。ファイルの読み込みが2回になるが、処理は軽い |
| 映像と同じプロセスで、2本目のパイプに書き出す | プロセスは1つで済む。標準出力以外のパイプを子プロセスに渡す方法がOSで異なり、特にWindowsで手間がかかる |

### 選んだ方式

**cpal**で既定の出力機器を開き、**映像とは別のffmpegプロセス**で音を取り出す。cpalを選んだのは、音を映像の時計に合わせるには、出力機器に渡す波形を自分で決められるほうが単純なためである。

### 実装

| 項目 | 実装 |
| --- | --- |
| 音の取り出し | ffmpegで最初の音声トラックを、出力機器のサンプリング周波数の32bit浮動小数点・ステレオに変換して、パイプに書き出す。読み取り用スレッドが2秒分を先に受け取っておく。動画の先読みと同時に始める |
| 映像との時刻の基準 | 映像も音もファイルの先頭（時刻0）から始める。映像が遅れて始まるファイルでは最初のフレームを繰り返し（`-fps_mode cfr`）、音が遅れて始まるファイルでは先頭を無音で埋める（`aresample=async=1:first_pts=0`）。こうして映像と音の差を0にそろえる。動画の長さは「ファイルの先頭から映像の終わりまで」とする |
| 時計 | 描画スレッドが使う再生時刻（上映開始からの秒数）を、音声出力も使う |
| 同期 | 出力機器が波形を求めるたびに、「今の時刻＋機器が報告する出力の遅延」から、この波形が聞こえる時刻を求める。各動画の音がどこまで鳴ったかと比べ、差が30msを超えたら、音を飛ばすか無音を入れて合わせる。30ms以下の差は、途切れを避けるため直さない。鳴り始めは、求めた時刻に当たるサンプルから正確に始める |
| 音量 | クロスフェードの間、音量を映像の不透明度と同じにする（線形）。音量の変化は、出力機器に渡す1回分の波形の中でなめらかに変える |
| チャンネル | 動画の音はステレオにそろえる（5.1chなどはffmpegでステレオに変換する）。出力機器がモノラルなら左右を混ぜ、3チャンネル以上なら最初の2チャンネルに出す |
| 計測 | 出力の遅延、映像に対する音のずれ（補正前の値）、その最大値、補正の回数、音の途切れ（デコードが間に合わなかった回数）を管理画面に表示する |

関連するコード:

- [`crates/fluxlide-engine/src/audio.rs`](../crates/fluxlide-engine/src/audio.rs): 音声出力とミキサー
- [`crates/fluxlide-engine/src/media/audio.rs`](../crates/fluxlide-engine/src/media/audio.rs): ffmpegによる音の取り出し
- [`crates/fluxlide-engine/src/slideshow.rs`](../crates/fluxlide-engine/src/slideshow.rs): 動画の開始と音の開始、音量のフェード
- [`src-tauri/src/presentation.rs`](../src-tauri/src/presentation.rs): 上映時に音声出力を開く

## 4. 結果

上映ウィンドウを使わず、描画エンジンを60Hzの間隔で呼び出しながら、実際の出力機器で音を鳴らして計測した（計測用の一時的なプログラムによる。リポジトリには含めていない）。写真→動画→写真→動画を繰り返し、32秒流した。

| 確認項目 | 結果 |
| --- | --- |
| 出力の遅延（機器の報告値） | 12.9ms |
| 映像に対する音のずれ | 最大0.3ms |
| ずれの補正 | 0回 |
| 音の途切れ | 0回 |
| 読み込みが間に合わなかった切り替え | 0回 |
| 44.1kHzの音声 | 48kHzに変換され、ずれは他の動画と同じ程度だった |
| 上映ウィンドウでの見た目と音 | 確認用の動画を写真の間に入れて上映し、光と音のずれ、切り替えでの音のフェードに問題は見られなかった（内蔵スピーカー、目と耳による確認。計測値は記録していない） |

自動テスト（`cargo test --workspace`）では、次のことを確かめている。

- 音が、決めた時刻に当たるサンプルから鳴り始める
- 遅れて鳴り始めた音は、遅れた分を飛ばす
- 30msを超えるずれは補正し、それ以下は補正しない
- 音量の変化がなめらかにつながる
- 音が0.5秒遅れて始まる動画で、先頭が無音で埋まり、全体の長さが映像と同じになる（ffmpegがない環境では飛ばす）

### 音が先に終わる動画

最初の実装では、音が映像より少し先に終わる動画（AACでは数十ms短いことが多い）で、終わった後も「ずれ」を測り続けていた。そのため最大のずれが23msと表示された。鳴り終えた音は計測と補正の対象から外すように直した。

### 計測値の意味

ここでいう「ずれ」は、音が実際に何サンプル鳴ったかと、描画の時計から求めた「鳴っているはずの位置」との差である。出力機器の時計と描画の時計の進み方の違いや、処理の遅れを表す。

一方、映像が画面に出るまでの遅れは含まない。描画した映像は次の垂直同期以降に表示されるため、60Hzの画面では映像が音より1〜2フレーム（17〜33ms）遅れて見える可能性がある。これは目と耳で確かめる必要がある。

### 上映ウィンドウでの確認手順（再確認用）

1. `npm run tauri dev` で起動し、「素材を追加…」で写真、確認用の動画、写真の順に選ぶ。確認用の動画は次のコマンドで作れる。1秒ごとに画面が白く光り、同時に「ピッ」と鳴る。

   ```bash
   ffmpeg -f lavfi -i "color=c=black:s=1920x1080:r=60,drawbox=x=0:y=0:w=iw:h=ih:color=white:t=fill:enable='lt(mod(t\,1)\,0.1)'" -f lavfi -i "sine=f=1000:sample_rate=48000,volume='if(lt(mod(t,1),0.1),0.5,0)':eval=frame" -t 10 -c:v libx264 -pix_fmt yuv420p -c:a aac av-sync-check.mp4
   ```

2. 上映を始め、光と音が同時か、音が先か後かを確かめる。切り替えのとき、音が映像と一緒にフェードするかも確かめる。
3. 管理画面の「映像に対する音のずれ」「ずれの補正」「音の途切れ」が増えないかを見る。

## 5. 判断

動画の音は、cpalで出力し、映像とは別のffmpegプロセスで取り出す方式で進める。描画エンジン単体の計測では、描画の時計に対する音のずれは1ms未満に収まった。上映ウィンドウでも、目と耳で分かるずれはなかった。映像が画面に出るまでの遅れの補正は、今のところ入れない。WindowsとLinux、遅延の大きい出力機器での確認が終わるまでは方式を確定しない。

## 6. 未確認の項目

- 映像が画面に出るまでの遅れ（1〜2フレーム）の実測。内蔵スピーカーと内蔵ディスプレイでは目と耳で分かるずれはなかったが、表示の遅れが大きい外部ディスプレイやテレビでは、音の開始を遅らせる補正が要る可能性がある
- WindowsとLinuxでの動作（WASAPI、ALSA。LinuxではPipeWireやPulseAudioをALSA経由で使う場合の遅延）
- Bluetooth機器など、出力の遅延が大きい機器。機器が報告する遅延が実際と合っているか
- 出力機器の切り替えや抜き差し。今は上映開始時の既定の出力機器を開いたままで、切り替えには追従しない
- 長時間の再生での、出力機器と描画の時計のずれ。今回は32秒のみ確認した
- BGM、BGMを動画の音に合わせて下げる処理（技術課題4番の残り）
- 音量のフェードの曲線。今は線形で、クロスフェードの中ほどで音が小さく感じる可能性がある
- 音声トラックが複数ある動画（最初のトラックのみ鳴らす）、5.1chなどのステレオへの変換の質
- 1本の動画につきffmpegのプロセスが2つになることの負荷
