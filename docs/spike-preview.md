# 技術検証: 管理画面の中のプレビュー

> 実施日: 2026-10-21。Linux（クラウド上のコンテナ、GPUなし）で、仮想ディスプレイ（Xvfb）の上でアプリを動かし、画面写真で確認した。描画はソフトウェアのVulkan（Mesaのllvmpipe）、webviewはWebKitGTK。macOS、Windows、実際のGPUでは確かめていない。

## 1. 目的

[完成までの手順](roadmap.md)の段階1の4番として、管理画面（webview）の中に、描画エンジンが描いた絵をどう出すかを決める。編集中のスライドショーを、上映と同じ見た目で確かめられるようにするためである。

## 2. 候補

| 候補 | 内容 | 判断 |
| --- | --- | --- |
| **画面外に描いて、画素をwebviewに送る** | 上映と同じ描画を `OffscreenTarget` に描き、RGBAで読み戻して、Tauriのコマンドの結果（バイナリ）としてページに渡す。ページは `<canvas>` に描く | **採用** |
| webviewの上にネイティブの描画面を重ねる | 管理ウィンドウに子ウィンドウ（NSView、HWND、X11のウィンドウ）を作り、wgpuの描画面を置いて、ページの中の枠の位置に合わせる | ページのスクロールや大きさの変化に位置を合わせ続ける必要がある。ダイアログやメニューが描画面の下に隠れる。Waylandでは子ウィンドウの位置を決められない。OSごとの実装が要る |
| webviewのWebGPUで描く | 描画をwebviewの中に移す | WebKitGTK（Linux）などWebGPUがないwebviewがある。描画をRustに集めるという方針（[技術選定](tech-stack.md)）にも反する |
| 動画として流す（MJPEGなど） | 独自のURLから連続した画像を流し、`<img>` で見せる | 独自のURLで、終わりのない応答を流せるかがwebviewによって違う。エンコードの手間もかかる |

採用した方式は、OSに依存する部分がなく、上映、書き出しと同じ `Compositor` で描くので、見た目も同じになる。代わりに、毎フレームの読み戻しと、webviewへの受け渡しの分だけ重い。プレビューは管理画面の一部の大きさで足りるので、その重さは許せると考えた。

## 3. 実装

| 項目 | 実装 |
| --- | --- |
| 描画 | プレビュー用のスライドショーを、上映と同じ作り方（`build_slideshow`。キャプション、置き方）で作り、自分の時計で進める。音は出さない |
| 大きさ | ページが、`<canvas>` の表示の大きさ×画面の倍率（2倍まで）を指定する。最大1920×1080 |
| 受け渡し | `preview_frame` コマンドが、RGBAの画素の後ろに幅と高さ（各4バイト）を付けたバイナリを返す。ページは `ArrayBuffer` で受け取り、コピーせずに `ImageData` にして `putImageData` で描く |
| 間隔 | ページは、前のフレームを描き終えてから次を頼む（画面の更新ごとに最大1回）。webviewが遅いときは、フレームが溜まらずに間隔が延びる |

関連するコード:

- [`src-tauri/src/preview.rs`](../src-tauri/src/preview.rs): プレビューのコマンド
- [`src/routes/+page.svelte`](../src/routes/+page.svelte): `<canvas>` への描画と、間隔・所要時間の表示

## 4. 結果

テストパターン（素材なし）で計測した。数値は、管理画面に表示した、1秒ごとの平均である。

| 大きさ | フレームレート | 1フレームの往復（頼んでから描き終えるまで） |
| --- | --- | --- |
| 640×360 | 54.6 fps | 18.0 ms |
| 1280×720（画面の倍率2） | 9.9 fps | 83.2 ms |

- 640×360では、画面の更新（60Hz）に近い間隔で動いた。
- 1280×720では遅かった。この環境は描画もwebviewもCPUで行っており、[動画への書き出し](spike-export.md)の計測から見ると、描画と読み戻しが1フレームあたり30ms台、残りの40〜50msがwebviewへの受け渡しと `putImageData` と見積もられる。どこが重いかは、実際のGPUを持つ機械で分けて測る必要がある。
- プレビュー中も、管理画面の操作は止まらなかった。

## 5. 判断と次の作業

管理画面のプレビューは、画面外に描いた画素をコマンドの結果として送り、`<canvas>` に描く方式で進める。

- 実際のGPUと、macOS（WKWebView）、Windows（WebView2）で、640×360と1280×720の速さを測る。
- 足りなければ、次の順に試す: プレビューの大きさを抑える（960×540まで）、読み戻しを2つのバッファで交互に行う、JPEGなどに圧縮して受け渡しの量を減らす、`ImageBitmap` と `drawImage` で描く。
- 編集の画面（段階3以降）では、再生時刻を指定して1枚だけ描く使い方（タイムラインの位置を動かしたとき）も要る。今のコマンドは、プレビューを始めてからの時間で描くだけである。
- プレビューの音。上映と同じミキサーで鳴らすか、音なしのままにするかは、編集画面の設計（段階3）で決める。
