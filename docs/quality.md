# 品質を上げる（段階6）

> 決定日: 2026-10-22。[完成までの手順](roadmap.md)の段階6。会場で起きることへの備え、長時間の再生、素材の対応範囲を決め、作ったことと確かめたことを書く。

## 1. 機器の抜き差し

| 起きること | 扱い | 作り |
| --- | --- | --- |
| 出力先の画面が外れる（ケーブルが抜ける、プロジェクターの電源が切れる） | 2秒ごとに出力先の画面を探す。見つからなければ一時停止し、操作画面に「出力先の画面が見つからないので、一時停止しました」と出す。同じ名前の画面がつながると、上映ウィンドウをその画面に戻して全画面にする。続けるのは操作する人が「再開」を押してから | `presentation.rs` の `watch_screen`。OS は外れた画面のウィンドウを残った画面（たいてい操作用の画面）に動かすので、観客に見せない時間に止めておく |
| 上映ウィンドウが閉じられる（Alt+F4 など） | 後片付けをして、操作画面を編集に戻す | `presentation.rs` の `WindowEvent::Destroyed` |
| 音の出口が変わる（Bluetooth のスピーカーをつなぐ・外す、イヤホンを挿す） | 1秒ごとに OS の既定の出口を見る。使っている出口が外れたか、既定が別の出口に変わったら、同じミキサーのまま新しい出口につなぎ直す。鳴っている動画の音と BGM はそのまま続く。どの出口もないときは、1秒ごとにつなぎ直しを試す | `audio.rs` の `AudioOutput::follow_device`。新しい出口にはミキサーと同じサンプルレートを頼み、違えば OS に変換させる |
| 素材が読めない（取り込んだあとで消えた、壊れた） | そのスライドを飛ばして次へ進み、操作画面に理由を出す。すべてのスライドが続けて読めなければ、読み込みをやめる | 段階1から（`Slideshow::start_loading`）。試験あり |

新しい音の出口は、音を出さない状態で開いてから前の出口と入れ替える。開けなければ（ミキサーのサンプルレートを受け付けない、まだつながりきっていない）前の出口のまま、1秒後にまた試し、理由を操作画面に出す。アンダーランのように音の仕組みが自分で戻るエラーでは、つなぎ直さない。

分かっている制限:

- 画面は名前で探す。同じ名前の画面が2台あると、片方が外れても気づかない。名前の取れない画面は「画面N」になり、手前の画面が外れると番号がずれる
- 音の出口も名前で比べる。同じ名前の別の出口に変わっても、つなぎ直さない

音の出口と画面のつなぎ直しは、実際に抜き差しして確かめていない（[手動の確認項目](manual-checks.md)）。

## 2. 長時間の再生

`crates/fluxlide-engine/examples/soak.rs` で、ループする作品（4032×3024 の写真2枚、音つきの動画、キャプション、ウォーターマーク、BGM、動画中の BGM の下げ）を、画面外に描きながら実時間より速く流した。時計は1フレームずつ進め、読み込みとデコードは待つ。

```text
cargo run --release -p fluxlide-engine --example soak -- <作業用フォルダ> <時間>
```

環境は Windows 11、NVIDIA GeForce RTX 4070 Ti（Vulkan）、1280×720・30fps。実時間の約40倍で流れ、24時間ぶんで読み込みの失敗と遅れはなかった。

### 2.1 メモリ

| 計測 | 開始 | 2時間 | 24時間 | Rust が確保した量 |
| --- | --- | --- | --- | --- |
| 改善の前（ワーキングセット） | 198 MB | 433 MB | 521 MB | 記録なし |
| 改善の前（プライベートバイト） | 408 MB | 562 MB | 966 MB | 21〜23 MB |
| 改善の後（プライベートバイト） | 182 MB | 655 MB | 715 MB | 21〜23 MB |

分かったこと:

- Rust が確保したメモリ（計測用のアロケータで数えた）は、24時間を通して 21〜23 MB で増えない。増えているのはその外で、GPU ドライバと wgpu が確保したメモリである。
- 増え方は段になっている。初めの1〜3時間で頭打ちになり、そのあとは1時間に数 MB。同じ設定でも回によって段の大きさが変わる（写真だけの1時間で 283〜428 MB）。
- 写真だけの作品で増え、動画だけの作品では増えなかった。ぼかし背景、キャプション、ウォーターマークを外しても増える。テクスチャを作って捨てるだけ（4000回）なら増えなかったので、どの処理がドライバ側の確保を増やすのかは突き止められていない。描画のたびに `device.poll` を呼んでも変わらなかった。

入れた改善:

| 改善 | 効果 |
| --- | --- |
| 大きな JPEG を画面に要る大きさまで縮めながら展開する（`jpeg-decoder` の縮小展開） | 写真を読むときの一時的なメモリが 108 MB から 39 MB になった。1200万画素の写真の読み込みも速くなる |
| wgpu に `MemoryHints::MemoryUsage` を渡し、GPU のメモリを小さな塊で確保させる | 開始時のプライベートバイトが 408 MB から 182 MB になった。描画の速さは計測で変わらなかった |
| 描画の方式（Vulkan と DirectX 12）を比べた | Windows の NVIDIA では Vulkan の方が 100 MB ほど少なかった。既定（wgpu が選ぶ Vulkan）のままにする。`WGPU_BACKEND` で切り替えられる |

上映ウィンドウ（`Presenter`）への表示と、実際の音の出口は、この計測に入っていない。管理画面（webview）のメモリも別にかかる。実機で数時間流す確認は[手動の確認項目](manual-checks.md)に入れた。

## 3. 素材の対応範囲（v1.0）

| 素材 | 対応 | 理由と作り |
| --- | --- | --- |
| JPEG・PNG | 対応 | `image` で読む。EXIF の向きを反映する |
| HEIC・HEIF（iPhone の写真） | 対応 | `image` では読めないので、取り込むときに FFmpeg で JPEG にして作品に残す。中身が JPEG の .HEIC（書き出しサービスに多い）はそのまま読む。**本物の HEIC のファイルではまだ確かめていない**（手元に HEVC で符号化した HEIC がなかった）。タイルに分かれた HEIC は FFmpeg 7.1 以降が組み立てる |
| H.264・HEVC の動画（mp4・mov・m4v） | 対応 | 同梱する FFmpeg の HEVC デコーダは LGPL の範囲に入っている。10bit の HEVC も 8bit にして再生できることを確かめた |
| 縦向きの動画（回転の情報を持つ動画） | 対応 | FFmpeg が回してから渡すので、縦の動画として表示される。取り込みで縦の大きさになることを試験で確かめる |
| 色プロファイル（Display P3 など） | sRGB として扱う | ICC プロファイルは読まない。P3 の写真は少し彩度が低く見える。上映と書き出しで同じ見た目になることを優先した |
| HDR の動画（PQ・HLG） | 再生できるが、色は変換しない | 同梱する FFmpeg には HDR から SDR へのトーンマッピング（zscale、libplacebo）がない。PQ の動画は色が薄く見える。v1.0 では README の「できないこと」に書く |
| そのほかの形式（GIF、WebP、AVI など） | 対応しない | 取り込みで「対応していない種類のファイルです」と断る |

## 4. 自動テスト

| 範囲 | 増やしたもの |
| --- | --- |
| エンジン | 書き出しに BGM が入って最後に消えること、書き出しが BGM のデコードを待つこと |
| Rust 側 | HEIC の取り込み（中身が JPEG のもの、FFmpeg で変換するもの、読めないもの）、縦向きの動画の大きさ |
| 画面側 | vitest を入れた（`npm test`、CI でも走る）。編集を順に送ること、送る変更が残る間は古い返事を出さないこと、閉じた作品の変更を捨てること、やり直しても通らないときに知らせること。時間とファイルの大きさの書き方 |

画面を操作する試験（E2E）は入れていない。上映ウィンドウは webview を持たず、WebDriver では操作できないため、[手動の確認項目](manual-checks.md)で確かめる。
