# 技術検証: 動画への書き出し

> 実施日: 2026-10-21。Linux（クラウド上のコンテナ、GPUなし）で、ソフトウェアのVulkan（Mesaのllvmpipe）とUbuntuのFFmpegを使って確認した。実際のGPUと、同梱するLGPL版のFFmpegでは確かめていない。

## 1. 目的

[技術選定](tech-stack.md)の「最初に検証する技術課題」5番（リアルタイムと動画書き出しの表示差、CPU/GPU/RAMの実測）として、次を確かめる。

- 上映と同じ描画で、スライドショーを動画ファイルに書き出せるか
- 上映の画面と、書き出したファイルの見た目の差
- 書き出しにかかる時間と、CPU・メモリの使用量、どこに時間がかかるか

## 2. 方式

```
Slideshow（1フレームずつ進む時計）
  → Compositor（上映と同じ描画）→ OffscreenTarget → RGBAで読み戻し
  → 書き込み用スレッド → パイプ → ffmpeg（映像のエンコード）→ 一時ファイル（.mkv）
  → OfflineMixer（書き出し用、音ズレ補正なし）→ 一時ファイル（32bit浮動小数点の生の音）
最後に ffmpeg で映像と音をまとめ、AACに変換して .mp4 にする
```

| 項目 | 実装 |
| --- | --- |
| 時計 | 実際の時間ではなく、1フレーム（30fpsなら1/30秒）ずつ進める |
| 待ち | 次の素材の読み込みや動画のデコードが間に合わないときは、同じ時刻で描き直しながら待つ（`Slideshow::is_waiting`）。上映では遅れとして表に出るが、書き出したファイルには遅れが残らない。音も、デコードが追いつくまで待ってから混ぜる（`OfflineMixer::has_samples_for`） |
| 再生の範囲 | 素材を1周だけ流し、最後の素材のあとは黒にフェードして終わる（`Slideshow::play_once`） |
| 映像のエンコード | 読み戻したRGBAを `ffmpeg` の標準入力に流す。書き込みは別スレッドで行い、2フレームまで溜めて、描画とパイプへの書き込みを重ねる |
| 色 | 描画はsRGBのRGBA（0〜255）。BT.709・リミテッドレンジのYUV 4:2:0に変換し、そのことをファイルに書く。`ffmpeg` の既定ではRGBからの変換にBT.601を使うため、明示した |
| エンコーダ | `ffmpeg -encoders` を見て、`h264_videotoolbox`（macOS）、`h264_mf`（Windows）、`libx264`、`libopenh264`、`mpeg4` の順に、最初にあるものを使う。同梱するLGPL版にはOSのエンコーダしかない（[FFmpegの同梱](spike-ffmpeg-bundling.md)）。`libx264` は開発中に使うGPL版（Linuxのパッケージなど）にだけある |
| 音 | 上映と同じミキサーで、書き出し用のモード（音ズレ補正を受け付けない）で混ぜる。映像のフレームごとに、そのフレームの時間分を、ファイル全体でずれが積もらないよう整数のサンプル数で作る |
| 映像と音をまとめる | 映像と音を1つの `ffmpeg` に同時に渡すには、標準入力のほかにもう1本パイプが要り、Windowsでは子プロセスに渡すのが手間である。そのため音は一時ファイルに書き、最後にまとめる。映像は再エンコードしない |
| 中止 | フラグで止める。途中のファイルと一時ファイルは消す |

関連するコード:

- [`crates/fluxlide-engine/src/export.rs`](../crates/fluxlide-engine/src/export.rs): 書き出し
- [`crates/fluxlide-engine/src/slideshow.rs`](../crates/fluxlide-engine/src/slideshow.rs): 1周だけの再生、待ちの判定
- [`crates/fluxlide-engine/src/audio.rs`](../crates/fluxlide-engine/src/audio.rs): `OfflineMixer::has_samples_for`
- [`crates/fluxlide-engine/examples/export_bench.rs`](../crates/fluxlide-engine/examples/export_bench.rs): 計測用のプログラム

## 3. 確認環境

| 項目 | 内容 |
| --- | --- |
| OS | Ubuntu 24.04.5（クラウド上のコンテナ） |
| CPU | 4コア、メモリ15GB |
| GPU | なし。Mesaのllvmpipe（LLVM 20.1.2）によるソフトウェアのVulkan |
| FFmpeg | 6.1.1（Ubuntuのパッケージ版。GPL版で `libx264` がある） |

素材は計測用のプログラムで作った。写真（4032×3024のJPEG、細かい粒状の模様入り）→動画（1920×1080・30fps・6秒、音あり）→写真→動画→写真の5つ。キャプション、スライドのトランジション、文字のウォーターマーク、ぼかし背景の置き方を使った。

## 4. 結果

`/usr/bin/time -v cargo run --release -p fluxlide-engine --example export_bench -- <作業用フォルダ> [エンコーダ]` で計測した。書き出しは1920×1080・30fps、23秒（690フレーム）。

### 見た目の差

上映中の写真の真ん中の時刻（2.5秒）について、上映で描かれる画素（同じ描画を画面外に描いて読み戻したもの。上映ウィンドウとは描き先が違うだけで同じ処理）と、書き出したファイルをデコードした画素を比べた。

| エンコーダ | PSNR（平均） | SSIM | ファイルの大きさ |
| --- | --- | --- | --- |
| `libx264`（CRF 18） | 42.8 dB | 0.988 | 12.2 MB |
| `mpeg4`（`-q:v 2`） | 41.6 dB | 0.975 | 36.6 MB |

- 目で見比べて、キャプションの文字、ぼかし背景、色の違いは分からなかった。差のほとんどは、YUV 4:2:0（色の解像度が縦横半分）への変換と圧縮によるものである。
- 音は、写真の区間で無音、動画の区間で動画の音が入っていた。

### 時間とCPU・メモリ

| 項目 | `libx264` | `mpeg4` |
| --- | --- | --- |
| かかった時間 | 59.8秒（実時間の0.38倍の速さ） | 47.2秒（0.49倍） |
| 1フレームあたり | 86.7ms | 68.4ms |
| うち描画の完了待ちと読み戻し | 56.0秒 | 記録せず |
| うち素材の読み込み待ち | 0.5秒 | 記録せず |
| うちエンコーダの待ち | 1.1秒 | 記録せず |
| CPU時間（ffmpegを含む） | 249秒（約3.2コア分） | 156秒 |
| 最大のメモリ（最も大きいプロセス） | 610 MB | 378 MB |

- この環境ではGPUの処理をCPUで行っている（llvmpipe）。描画の完了待ちが時間のほとんどを占め、エンコードや素材の読み込みは足を引っ張っていない。実際のGPUでは描画は数ms程度と見込まれ、そのときはエンコーダの速さで決まるはずである。実際のGPUを持つ機械での計測が要る。
- 最大のメモリは、llvmpipeの作業領域を含む計測用プログラムのものと思われる。`ffmpeg` を含めた合計ではない。

## 5. 分かったこと

- 上映と同じ `Compositor` を画面外に向けるだけで、書き出しは上映と同じ見た目になる。差は動画の形式（YUV 4:2:0）と圧縮によるものだけである。
- 読み込みやデコードが遅れても待てばよく、書き出したファイルに遅れは残らない。
- 音を一時ファイルにして最後にまとめる方式は、どのOSでも同じ作りで済む。まとめる処理は1秒程度だった。

## 6. 未確認のことと次の作業

- 実際のGPU（Metal、Direct3D 12、Vulkan）での速さ。読み戻しを2つのバッファで交互に行い、GPUの描画とCPUへのコピーを重ねる工夫は、計測してから決める。
- 同梱するLGPL版のFFmpegでの `h264_videotoolbox`（macOS）、`h264_mf`（Windows）での書き出し。ハードウェアのエンコーダはビットレート指定にしたが、写真が多い動画での画質は確かめていない。
- LinuxでのH.264の書き出しの方式（[FFmpegの同梱](spike-ffmpeg-bundling.md)の5.4）。今のLGPL版のLinuxでは `mpeg4` しか使えない。
- 書き出しにBGMを入れる。BGMはミキサーの `Source` なので、書き出し用のミキサーに足せば動く作りだが、デコードの待ちの仕組みがBGMにはまだない。
- 色: ファイルにはBT.709と書いたが、描画はsRGBのガンマで行っている。多くのプレーヤーではほぼ同じに見えるが、暗い部分のわずかな差は確かめていない。
- 書き出し画面（段階5）: 用途ごとの設定、所要時間の目安、進み具合、中止。今は関数とテストと計測用のプログラムだけで、管理画面からは呼べない。
