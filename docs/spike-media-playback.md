# 技術検証: 写真と動画の連続再生

> 実施日: 2026-10-20。macOSで、描画エンジン単体の計測と、上映ウィンドウでの写真→動画→写真の再生を確認した。Windows、Linuxは未確認。

## 1. 目的

[技術選定](tech-stack.md)の「最初に検証する技術課題」1番（メディア素材を読み込み、動画を連続再生できるか）について、次の2点を決める。

- 動画をデコードする方式
- 写真と動画を混ぜて、切り替えで黒画面や止まりを出さずに再生する仕組み

## 2. 方式

### 動画デコードの候補

| 候補 | ビルド | 配布（3OS） | ライセンス・特許 | GPUへの渡し方 |
| --- | --- | --- | --- | --- |
| **FFmpegのコマンドを別プロセスで動かす** | 依存なし。Rustのコードだけでビルドできる | `ffmpeg` と `ffprobe` の実行ファイルをOSごとに同梱する（Tauriの `externalBin`）。1本あたり数十MB | LGPL版のFFmpegを別プログラムとして同梱する。アプリ本体とリンクしないため条件を満たしやすい。H.264の特許の扱いは要確認 | パイプでCPUに受け取り、テクスチャへ書き込む |
| FFmpegのライブラリをリンクする（`ffmpeg-next`） | 各OSでFFmpegの開発用ファイルとlibclangが要る。WindowsのCIでは別途用意が要る | `.dll` / `.dylib` / `.so` を同梱する。macOSでは各ライブラリの署名も要る | LGPLの動的リンクなら可。特許は上と同じ | CPU経由が基本。ハードウェアデコードの結果をそのまま使うには追加の実装が要る |
| OS標準のデコーダ（macOS: AVFoundation・VideoToolbox、Windows: Media Foundation、Linux: GStreamer） | OSごとに別の実装が要る | 追加の同梱なし。ただしLinuxではH.264のプラグインが入っていない環境がある | OSのライセンスで使える。LinuxのGStreamerプラグインは配布元しだい | GPU上のフレームをコピーなしで使える可能性がある。wgpuとの受け渡しはOSごとに実装が要る |
| Rustのみのデコーダ（`openh264` など） | ビルドできる | 同梱なし | 特許の許諾はCiscoが配布するバイナリを使う場合に限られる。MP4の分離（demux）は別に要る | CPU経由 |

### 選んだ方式

**FFmpegのコマンドを別プロセスで動かす方式**を選んだ。理由は次のとおり。

- ビルドにFFmpegが要らないため、3OSのCIをそのまま通せる。
- アプリ本体とリンクしないため、LGPL版のFFmpegを同梱しやすい。壊れたファイルでFFmpegが落ちても、アプリは落ちない。
- 1つのコマンドでMP4以外の形式も扱える。

GPUへの渡し方はCPU経由になる。4Kでも追いつくかは下の計測で確かめた。OS標準のデコーダは、CPU経由で性能が足りない場合の移行先とする。

### 実装

| 項目 | 実装 |
| --- | --- |
| 写真 | `image` クレートでJPEG・PNGを読み込み、EXIFの向きを反映し、出力画面に収まる大きさまで縮小して、sRGBのテクスチャにする |
| 動画の情報 | `ffprobe` で長さとフレームレートを取得する。60fpsを超える動画は60fpsで取り出す |
| 動画のデコード | `ffmpeg` で出力画面に収まる大きさまで縮小（拡大はしない）し、BT.709・リミテッドレンジのYUV 4:2:0に揃えて、YUV4MPEG2形式でパイプに書き出す。読み取り用スレッドが8フレーム先まで受け取っておく |
| 動画の表示 | 描画スレッドが、再生時刻に当たるフレームをY・U・Vの3枚のテクスチャに書き込む。シェーダーでRGBに変換する。間に合わないときは前のフレームを表示したままにする |
| 先読み | ある素材を表示し始めた時点で、次の素材を別スレッドで準備する。写真は読み込みとテクスチャ作成まで、動画は最初のフレームをテクスチャに書き込むまで済ませる |
| 切り替え | 次の素材の準備ができてから、1秒のクロスフェードを始める。準備が遅れた場合は今の素材を表示し続け（動画は最後のフレームで止める）、遅れを記録する。写真は5秒表示する。動画は最後のクロスフェードが終わる時点で終わるよう、終わりの1秒前からフェードを始める |
| 重ね方 | 2枚を不透明度で足し合わせる（加算合成）。縦横比が違って一方にしかない部分も、黒へのフェードと同じ明るさの変化になる |
| 再生順 | 管理画面で選んだ順に流し、最後まで行ったら最初に戻る。読み込めない素材は飛ばす |
| FFmpegの場所 | 環境変数 `FLUXLIDE_FFMPEG_DIR`、実行ファイルと同じフォルダ（同梱した場合の場所）、`PATH`、macOSでは `/opt/homebrew/bin` と `/usr/local/bin` の順に探す |
| 管理画面 | 素材の追加（ファイル選択ダイアログ）、並べ替え、取り外し。上映中は、表示中の素材、切り替えの回数、読み込みが間に合わなかった回数、動画のデコード遅れなどを表示する |

関連するコード:

- [`crates/fluxlide-engine/src/media.rs`](../crates/fluxlide-engine/src/media.rs): 写真の読み込み、テクスチャ
- [`crates/fluxlide-engine/src/media/video.rs`](../crates/fluxlide-engine/src/media/video.rs): FFmpegによるデコード
- [`crates/fluxlide-engine/src/slideshow.rs`](../crates/fluxlide-engine/src/slideshow.rs): 先読みとクロスフェード
- [`crates/fluxlide-engine/src/presenter.rs`](../crates/fluxlide-engine/src/presenter.rs)・[`layer.wgsl`](../crates/fluxlide-engine/src/layer.wgsl): 素材の描画
- [`src-tauri/src/presentation.rs`](../src-tauri/src/presentation.rs): 上映ウィンドウでの再生
- [`src/routes/+page.svelte`](../src/routes/+page.svelte): 素材の選択

## 3. 確認環境

| 項目 | 内容 |
| --- | --- |
| OS | macOS 27.0.1 |
| 機種 | MacBook Pro、Apple M4 Pro、メモリ48GB |
| FFmpeg | 9.0.2（Homebrew版。GPLで構成されているため、配布には使えない） |
| 主なバージョン | wgpu 30.0.1、image 0.25.10、Tauri 2.12.4、tauri-plugin-dialog 2.8.3 |

素材はFFmpegで作った。

| 素材 | 内容 |
| --- | --- |
| 写真 | JPEG 4032×3024（細かい模様と、単色の帯の2種類）、PNG 1600×2400（縦長） |
| 動画 | H.264（High）1920×1080・30fps・8秒、H.264（High）3840×2160・30fps・6秒（40Mbps）、H.264 3840×2160・60fps・6秒（約150Mbps） |

出力画面の大きさは、内蔵ディスプレイと同じ3456×2234とした。

## 4. 結果

上映ウィンドウを使わず、描画エンジンを60Hzの間隔で呼び出して計測した（計測用の一時的なプログラムによる。リポジトリには含めていない）。

| 確認項目 | 結果 |
| --- | --- |
| 写真の読み込み（読み込みから縮小、テクスチャ作成まで） | 4032×3024のJPEGで90〜200ms、1600×2400のPNGで50〜70ms。開発ビルドでも画像関連のクレートを最適化すれば同程度（最適化しないと2〜6秒かかった） |
| 動画の準備（長さの取得から最初のフレームの書き込みまで） | 80〜350ms |
| 1080p・30fpsの再生 | 8秒間で、デコードが間に合わなかったフレームは0 |
| 4K・30fpsの再生（3456×1944に縮小） | 6秒間で、間に合わなかったフレームは1 |
| 4K・60fpsの再生（同上） | 6秒間で、間に合わなかったフレームは0〜1（リリースビルド）、6（開発ビルド） |
| 写真→動画→写真→動画を30秒流したとき | 切り替え5回のうち、読み込みが間に合わなかったのは0回。最初のフェードインの後、2枚の不透明度の和が1を下回ったフレーム（黒が透けるフレーム）は0 |
| 上映ウィンドウでの見た目 | 写真→動画→写真の順で再生し、目視で問題は見られなかった。計測値は記録していない |
| 動画の音 | 出ない。音声はまだ実装していない |

自動テスト（`cargo test --workspace`）では、写真どうしのクロスフェード、読み込めない素材を飛ばすこと、準備が遅れたときに今の素材が残ること、動画のフレームが再生時刻に合わせて進み最後で止まることを確かめている。GPUやFFmpegがない環境では、該当するテストを飛ばす。

### ハードウェアデコード

最初は `-hwaccel auto`（macOSではVideoToolbox）を指定していた。4Kの動画では、指定しない場合より遅れが多かった（6秒間で7〜12フレーム、指定しない場合は0〜1フレーム）。パイプで受け取るためにGPUからCPUへフレームを戻す処理と、その後の縮小が重いためと考えられる。現在はソフトウェアでデコードしている。代わりにCPUの使用量は多く、4K・60fpsのデコードと縮小に、およそ2コア分を使った。

### 上映ウィンドウでの確認手順（再確認用）

1. FFmpegを入れる（macOSでは `brew install ffmpeg`）。管理画面の「動画デコーダ」にバージョンが出ることを確かめる。
2. `npm run tauri dev` で起動し、「素材を追加…」で写真→動画→写真の順に選ぶ。
3. 出力先の画面を選んで上映を始める。切り替えのたびに黒画面や止まりがないか、動画の動きが滑らかかを目で見る。
4. 管理画面の「読み込みが間に合わなかった切り替え」「動画のデコード遅れ」「遅れたフレーム」が増えないかを見る。

## 5. 判断

動画のデコードは、FFmpegのコマンドを別プロセスで動かす方式で進める。描画エンジン単体の計測では、4K・60fpsの動画を含めて、先読みにより黒画面を出さずに写真と動画をつなげる見込みが立った。macOSの上映ウィンドウでも、写真と動画をつないだ再生を確認できた。WindowsとLinuxでの確認が終わるまでは方式を確定しない。

CPUの使用量が問題になる場合や、OSのデコーダでしか扱えない形式（HDR動画など）が必要になった場合は、OS標準のデコーダへの移行を検討する。そのため、描画エンジンは動画を「再生時刻に当たるフレームをテクスチャへ書き込むもの」として扱い、デコードの方式を差し替えられるようにしている。

## 6. 未確認の項目

- 上映ウィンドウでの計測値（フレームレート、切り替えの遅れ、動画のデコード遅れ）の記録
- WindowsとLinuxでの動作。特に次の点
  - 同梱したFFmpegを実行ファイルと同じフォルダから見つけられるか（Tauriの `externalBin` での同梱は未実装）
  - Windowsで、FFmpegのコンソールウィンドウが開かないか（開かない設定で起動しているが未確認）
- 配布に使うFFmpegの構成。LGPLで、H.264のデコーダだけを含む版を用意し、ライセンス表記と特許の扱いを確認する
- 音声。この試作では動画の音を再生していなかった。その後、[動画の音声と映像の同期の技術検証](spike-audio-sync.md)で音を鳴らす仕組みを加えた
- 色の扱い
  - 動画はすべてBT.709・リミテッドレンジ・8bitに揃えている。HDRや10bitの動画、BT.2020の動画は正しい色にならない
  - 写真の色プロファイル（Display P3など）を無視している。iPhoneの写真は少し色が浅くなる
- スマートフォンで撮った素材。EXIFの向きの反映と、回転情報を持つ動画（縦向きの動画）の表示は、実物で確かめていない
- 可変フレームレートの動画。FFmpegで一定のフレームレートに揃えているが、実物で確かめていない
- HEIC・HEVCなど、今回扱わなかった形式
- 長時間の連続再生でのメモリ使用量と、FFmpegのプロセスが残らないか
- 上映中に出力画面の大きさが変わった場合。素材は上映開始時の画面の大きさで読み込んでいる
- 動画の途中からの再生（シーク）。今は常に最初から流す
- 4K・60fpsでの画面の描画まで含めた負荷。CPUからGPUへの転送量は1秒あたり約600MBになる
